# Agent 框架卷错了地方

*缺的不是又一个控制层,是一个状态层。*

---

有一个问题,一问出来,整个 AI agent 圈就会安静下来:

> 你敢让 AI 自己给客户退款吗?

那些平时对自主 agent 信心十足的人,会在这儿犹豫。而这份犹豫是对的——不是因为模型*判断不了*该不该退(它通常判断得了),而是因为整个技术栈里,没有任何一环能拦住它把这笔款**退第二次**。它读一遍对话,判断「看起来我们还欠这位客户一笔退款」,调了退款 API;过一会儿客户又发来一条消息,它再读一遍对话,又退了一次。钱出去了,没有任何记录说明为什么,系统甚至根本不知道自己重复付款了。

这不是模型能力的问题。一个更聪明的模型,依然回答不了「这笔退款到底退过没有」——因为这个答案,根本不存在于任何它能信任的地方。

## 记忆,不是状态

今天的 agent 有的是**记忆**:一摞不断变长、每轮重读、太长了就摘要、偶尔还会读串的笔记。记忆是个好东西,但它只擅长一件事——记住*说过什么*。我们却一直拿它去干另一件它根本不擅长的事:知道*什么是真的*。

这是两种不同的载体:

- **记忆**回答的是*「客户跟我们说了什么?」*。你往里追加、从里召回、把它摘要。模糊一点没关系。
- **状态**回答的是*「这笔退款退了没?这张工单关了没?我们答应过什么、兑现了没?」*。这里必须有且只有一个权威值,而且只能以受控的方式改变。

一个把「改变世界」的决策跑在记忆之上的 agent,只要回合数足够多,迟早会读到一条过期的笔记并据此行动。这不是你靠改 prompt 能绕开的 bug,而是一个范畴错误:用*说过什么*的载体,去回答*什么是真的*的问题。

## 整个生态,都在卷那个已经拥挤的层

看看力气都花在哪了。LangGraph、Dify、OpenClaw,上百个编排框架——它们做的全是**控制层**:谁来调度、怎么派活、*对话*的状态机怎么往前走。这是有价值的活,但也是一片深红的红海。

而在它下面,藏着一个更安静、几乎没人认领的问题:

> 现在世界的真相到底是什么?这个 agent 又被允许对它做哪些改变?

有一个细节能证明这个空白是真实存在的,而不是凭空想象。那些认真的 agent 产品,*确实*会用上有类型、有状态、带约束的对象——但只给自己用。它们会认认真真建一个状态机来管自己的提醒、自己的计费、自己内部的承诺。这个能力显然在它们手边,需要时它们立刻就上。它们只是从不把它指向**你的**世界——你的退款、你的工单、你的发货。治理全部朝内。朝外,朝着 agent 真正要碰的那个业务世界,什么都没有。

## 那个缺失的层,长什么样

四个原语。而最惊人的一点是:从一个行业换到另一个行业,变的东西少得出奇。

- **对象 Object** —— 一条有类型、持久化的记录,描述此刻的现状。一个 `Order`,一张 `Ticket`。有标识、能持久、有唯一权威的当前值。
- **动作 Action** —— 一等公民、*受治理*的操作,也是状态改变的唯一途径。它带一个前置条件(绑在对象状态上)、一个权限(绑在角色和额度上)、一个风险守卫(绑在派生事实上)、一个效果、一条事件。
- **事件 Event** —— 只增账本里的一条:谁、基于什么状态、为什么放行、结果如何。
- **投影 Projection** —— 当前状态是事件的累加结果。你可以把投影整个扔掉,仅凭事件就把它重建出来。

模型永远碰不到「效果」那一步。它只能*提议*一个动作——`request_action("issue_refund", …)`——由一个确定性引擎来裁决它发不发生。**模型提议,系统裁决。**

看看这套逻辑对那笔重复退款做了什么。你不是*检测*到第二次退款然后拒绝它。你把动作绑在状态上——`金额 ≤ 订单金额 − 已退金额`——一旦订单全额退过,剩余可退就是零,第二次退款不再是被*拦下*,而是在结构上**根本不可能发生**。同样的形状,也管住了「只发一次货」「只关一次单」「别超信用额度」。

再看看它对审计做了什么。当有人问「这单为什么退了 800?」,答案是账本里的一行——*由 anna 发起,sara 审批,原因:延迟发货*——而不是去聊天记录里做考古。审计不再是一个事后焊上去的功能,它*就是*存储模型本身。

## 一条有用的纪律:从决策倒推 ontology

这里潜伏着一个失败模式,值得点名,因为它专门杀死这类项目。你**绝不**该先画一个漂亮的领域模型,再回头去找它能干嘛——那样你等于在要求开发者把整个领域重写一遍,而回报他们还看不见。

要从另一头开始:*哪些动作必须被安全地完成?* 然后倒推——需要哪些对象、处于哪些状态,这些动作才被允许?决策需要什么字段,你就建什么字段,多一个都不建。ontology 是你所需治理的残留物,不是你先竖起来的纪念碑。

## 语法是横向的,词汇是你自己的

把客服模型,跟 CRM 模型、物流模型、审批模型摆在一起,同一套*语法*反复出现:状态转移要前置条件;改变靠状态实现幂等;权限按角色分级;超额转审批;缺字段不许收尾;到期的承诺变成被追踪的义务。「退款限额按角色」和「折扣限额按角色」和「放货要先收款」,是同一句话的不同说法。

这套语法是横向的,值得被标准化——就像「一笔支付」成了一个可复用的原语,就像「持久化执行」成了一个。而*词汇*——哪些对象、哪些阈值、接哪个系统——是按行业走的,那才是真正的 know-how 沉淀的地方。

## 它是什么,它不是什么

诚实地把话说全,包括那些容易跳过的部分。

它**不是**又一个 agent 框架,也不想去赢控制层。它坐在你已经在用的任何编排器下面。把它想成刹车和行车记录仪:模型负责思考;状态层管住那少数几下真正改变世界的动作,并把每一下都记下来。

它也**不**想做整个 agent。一段优秀的客服体验,大部分是理解意图、共情、写回复——那是模型的活。状态层是那条系在「会丢钱、会砸信任」的少数几个动作之上的安全带。别把安全带当成整辆车来卖。

还有一个该当面回答的尖锐质疑:*AI 写代码这么快,别人看懂不就能做?* 运行时代码,是的。可这恰恰说明:能防守的动作,是把抽象定对、把类别占进人们心智、把词汇和经过实战打磨的连接器沉淀下来——不是守着源码。代码便宜,是「为什么要开源、要快、要抢先」的理由,不是反对它的理由。

## 它开源了,这是 repo

这套论证的早一版,结尾写的是「所以我准备做一个 agent 框架」——这跟它自己的论点打架。这是纠正后的结尾:

它**不是**又一个 agent 框架。它是任何 agent 在动真实业务之前,都该先过的那道状态闸门。它开源,Apache-2.0,一条命令就能把整个东西跑起来:

```bash
git clone https://github.com/xl-1995/agentstate && cd agentstate
npm install && npm run demo
```

你会看到一个普通 agent 在一笔 150 的订单上付出去 300,然后看到同一个 agent——经过状态层——在第二次被当场拒绝,还附上一张能查的收据。
